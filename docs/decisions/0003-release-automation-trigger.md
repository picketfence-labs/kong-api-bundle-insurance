# ADR 0003: バージョン更新・レジストリpushの自動化トリガー

- **日付**: 2026-09-02
- **状態**: 決定

## コンテキスト
`main`へのマージ後、いつ・どうやってバージョンを更新し、コンテナイメージをGHCRへpushするかを決める必要がある。パブリックリポジトリへの公開・課金の発生しない操作である一方、一度pushしたパブリックイメージの公開は実質的に取り消しが難しい（不可逆に近い）操作でもある。

## 検討した選択肢
1. **`main`マージ時に自動実行**: `services/`等の対象ディレクトリに変更のあるPRが`main`にmergeされたら、GitHub Actionsが自動でパッチバージョンをインクリメントし、build・push・Release作成まで人手を介さず実行する。メリット: 運用が速く、都度の手動操作が不要。デメリット: 公開タイミングを人間が制御できない（意図しない内容が即座に公開される）。
2. **手動`workflow_dispatch`で実行**: `main`マージ後、明示的に`workflow_dispatch`を叩いた時だけバージョン更新・push・タグ付けを実行する。Picketfence Labsの別プロジェクト（GCPインフラのTerraform apply）で採用している「承認ゲート」パターンを踏襲し、公開タイミングを人間が制御できる。デメリット: 都度手動トリガーが必要で、運用の手間が増える。

## 決定
選択肢1（`main`マージ時に自動実行）を採用する。

## 判断基準・根拠
- 利用者から「main マージ時に自動実行」で明示的な指示を受けた（複数の妥当な選択肢がある判断ポイントのため、実装着手前に確認済み）
- 本リポジトリは元々公開予定のデモ用リポジトリであり、`main`へのマージ自体が実質的なレビューゲートとして機能する（PRレビュー→mergeの通常フローを踏んでいる前提）ため、追加の手動承認ゲートを設けるコストに対するメリットが薄いという判断

## 想定していたこと vs 実際どうだったか
- 実装後（PR #2）、`release.yml`のpathsフィルタ（`services/**`等）のため、実装自体を追加したマージでは一度も自動発火しないという初回起動時特有の問題が判明した。これは「日常運用としての手動トリガー」（選択肢2、当時不採用）とは別の課題であり、初回だけ発火手段が無い状態だったため、`workflow_dispatch`を**ブートストラップ専用の手動発火手段**として追加した（利用者に確認済み、2026-09-03）。日常運用は選択肢1（`main`マージ時に自動実行）のまま変わらず、選択肢2の再選択には当たらない

## 影響・トレードオフ
- 誤った内容を含むPRが`main`にmergeされた場合、即座にパブリックイメージとして公開されてしまう。PRレビューの質がそのまま公開物の品質に直結するため、`main`へのPRレビューを軽視しない運用が前提になる
- 誤って公開してしまった場合の対処（GHCR上の該当タグの削除・visibility変更等）は、実装タスクで手順を明確化しておくことが望ましい
