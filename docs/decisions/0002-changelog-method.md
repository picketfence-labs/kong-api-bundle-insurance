# ADR 0002: Change Logの実装方式

- **日付**: 2026-09-02
- **状態**: 決定

## コンテキスト
コンテナレジストリ（GHCR）へ公開するイメージについて、「何が変わったか」を追跡できるようにする（利用者依頼の「コンテナレジストリにChange Log登録」に対応）。GHCR自体にはネイティブなChange Log機能は無く、パッケージページはpush元のGitHub Releaseを自動的に紐づけて表示する仕様を利用する。

## 検討した選択肢
1. **GitHub Release + `CHANGELOG.md`の併用**: バージョンタグ作成時にGitHub Releaseを作成し、リリースノートを記載する。GHCRのパッケージページはpush元のRelease/タグを自動的にリンク表示するため、レジストリ側からも変更履歴が辿れる。`CHANGELOG.md`にも同内容を残し、リポジトリ単体でも履歴が読める状態にする。
2. **`CHANGELOG.md`のみ**: GitHub Releaseを作らず、リポジトリ内の`CHANGELOG.md`だけで履歴管理する。実装はシンプルだが、GHCR側からは辿れない（パッケージページにリリース情報が表示されない）。
3. **コミットメッセージのみ**: 専用のChange Logファイルを作らず、`git log`の履歴のみに委ねる。実装コストは最小だが、パッチバージョン単位でどう変わったかが一覧化されず、利用者依頼の「Change Log登録」の意図（レジストリ利用者が変更内容を追える）を満たさない。

## 決定
選択肢1（GitHub Release + `CHANGELOG.md`の併用）を採用する。

## 判断基準・根拠
- 利用者の意図は「コンテナレジストリを見た人が変更内容を追える」ことであり、GHCRパッケージページから直接辿れる選択肢1が最も直接的にこれを満たす
- `CHANGELOG.md`も併記することで、リポジトリ単体（GitHub UIやレジストリを経由しない参照）でも履歴が読める

## 想定していたこと vs 実際どうだったか
（Harness定義段階のため未実装。実際にCIパイプラインを運用してから追記する）

## 影響・トレードオフ
- CIパイプライン側でGitHub Release作成APIの呼び出しと`CHANGELOG.md`更新の両方を実装する必要があり、`CHANGELOG.md`のみの場合より実装コストがわずかに増える
- リリースノートの内容（何を書くか、コミットメッセージからの自動生成にするか等）は実装タスクで具体化する
